## Problem Statement

People sharing expenses need a dependable record of who paid, each person's share, direct debts and repayments. They need to correct mistakes without losing attribution or creating debt for departed members. SpendWise currently has approved designs but no backend application, dependency manifest, migrations or executable tests. The later mobile client needs working, verified APIs and a reachable test environment before detailed screens are designed.

## Solution

Build the agreed FastAPI and PostgreSQL backend with Supabase Auth. Deliver account/profile operations, groups and invitations, membership lifecycle, expenses, direct balances, recorded repayments and auditable corrections through the approved mobile-facing API. Complete the handoff with matching request/response examples, generated OpenAPI, the agreed lean verification evidence and a deployed HTTPS test environment using disposable data.

This is an implementation specification, not a claim of completed implementation or deployment. Preserve the approved database model and subsequent behavior decisions; investigate only concrete gaps. Detailed frontend screens and implementation follow backend readiness.

## User Stories

1. As a user, I want to register and sign in with Google or email/password, so that I can use one SpendWise identity across sessions.
2. As an email/password user, I want email verification and password reset through Supabase, so that I can establish and recover access.
3. As an unverified user, I want to manage my profile while group actions require verification, so that account setup and group eligibility remain clear.
4. As a user, I want an idempotently provisioned profile, so that retries and additional devices do not duplicate my identity.
5. As a user, I want to read my trusted account email and edit my display name, so that my account details are accurate and later sign-ins preserve my edits.
6. As a user, I want sign-out to affect only my current session, so that other devices remain signed in under the agreed token-expiry policy.
7. As a verified user, I want to create a named group with one supported currency and fixed timezone, so that shared entries use consistent money and date rules.
8. As an active member, I want equal permissions to other active members, so that group management does not depend on an administrator.
9. As an active member, I want to rename a group and change its currency before financial activity, so that I can correct setup details.
10. As an active member, I want currency to remain locked after the first financial entry even if deleted, so that historical money never changes meaning.
11. As a user, I want to list my active groups with separate owed and receivable totals, so that I understand each group's position without combining currencies.
12. As an active member, I want group details and active member counts, so that I can identify the group and its current participants.
13. As an active member, I want to read active and historical memberships without authentication emails, so that I can attribute entries without exposing account data.
14. As an active member, I want to create reusable seven-day invitation links, so that eligible people can join after explicit acceptance.
15. As an invitation recipient, I want a verified preview with the group name, currency and member count, so that I can decide whether to accept without receiving private group data.
16. As a recipient, I want repeated acceptance to return my existing membership, so that retries do not duplicate membership or join events.
17. As an active member, I want to list available invitations and revoke links, so that I can manage joining access without retrieving stored secrets.
18. As a group member, I want expired, revoked and inactive-group invitations to fail, so that unusable links cannot grant access.
19. As a settled member, I want to leave or be removed while retaining historical attribution, so that departure removes access without deleting records.
20. As a member, I want departure blocked until every direct debt involving me is zero, so that a zero overall net position cannot hide unsettled relationships.
21. As a departed member, I want to rejoin through a valid invitation using the same membership, so that history and identity remain continuous.
22. As the final active member, I want a fully settled departure to inactivate the group and invalidate invitations, so that an abandoned group cannot be joined again.
23. As a member, I want a departing invitation issuer's links revoked, so that their old invitations no longer grant access.
24. As an active member, I want to add an expense with a name, date, amount, one payer and participants, so that a shared cost is recorded accurately.
25. As an active member, I want a payer who need not participate in the allocation, so that I can record someone paying entirely for others.
26. As an active member, I want equal, exact-amount and percentage split methods, so that different sharing arrangements are supported.
27. As an active member, I want deterministic allocation of rounding remainders, including zero shares, so that allocated minor units always equal the total.
28. As an active member, I want invalid totals, percentages, participants, money and future dates rejected, so that invalid entries never affect balances.
29. As an active member, I want expenses and repayments in one newest-first transaction list, so that I can read the group's financial record.
30. As an active member, I want expense rows to show payer, amount, an automatic icon and my lent/borrowed/neutral position for that expense, so that repayments do not obscure its original allocation.
31. As an active member, I want distinguishable repayment rows with both parties, amount, date and payment metadata, so that recorded payments are clear.
32. As an active member, I want direct balances that offset mutual debt within each pair without rerouting through others, so that I can see who actually owes whom.
33. As an active member, I want to record a partial or full external repayment without recipient confirmation, so that balances reflect payments already made outside SpendWise.
34. As an active member, I want new repayments limited to the current debt in the chosen direction, so that they cannot overpay or invent debt.
35. As an active member, I want cash or a labelled other payment method, so that I can identify how a repayment was made without treating it as spending.
36. As an active member, I want to edit or soft-delete either kind of financial entry, so that mistakes can be corrected while records remain attributable.
37. As an active member, I want corrections after repayment to recalculate balances, including reversing debt between active members, so that corrected facts determine the current position.
38. As an active member, I want repayment corrections to retain the original parties without reapplying the creation debt cap, so that historical payment corrections remain possible.
39. As a departed member, I want corrections to preserve my zero direct balances, so that changes after departure cannot give me new debt or receivables.
40. As an active member, I want complete immutable before/after change history with actor and timestamp, so that corrections remain auditable without a history-browsing screen.
41. As an active member, I want stale financial edits rejected with the current version, so that concurrent work cannot overwrite newer changes.
42. As an API consumer, I want a financial submission retried with the same key and data to return its original result, so that network failures do not duplicate writes.
43. As an API consumer, I want changed data or targets under the same retry key rejected, so that a key cannot silently stand for another command.
44. As a removed member, I want current membership checks to deny subsequent group access and replay, so that an unexpired token does not retain group privileges.
45. As an API consumer, I want stable cursor ordering and a documented refresh model, so that I can traverse unchanged data and refresh after changes.
46. As an API consumer, I want consistent validation and error responses with request IDs, so that failures are actionable without revealing private internals.
47. As an API consumer, I want success only after database commit, so that a successful response represents durable financial state and history.
48. As a maintainer, I want repeatable migrations and restricted runtime/client grants, so that the approved integrity and access boundary survive deployment.
49. As a maintainer, I want compact automated API/database journeys plus focused boundary cases, so that essential behavior is proved without duplicate layer tests.
50. As a frontend developer, I want a reachable test API, real-auth smoke evidence, examples and connection instructions, so that mobile work can begin without building screens to verify the backend.
51. As a maintainer, I want documented disposable-data reset and compatible-revision recovery, so that test-environment failures are recoverable.
52. As the project owner, I want free-compatible hosting evaluated during implementation and approval before charges, so that early testing stays within the agreed budget.

## Implementation Decisions

- **Baseline and scope:** Use the glossary's Profile, Membership, Expense share, Repayment, Direct balance, Financial entry and Change history vocabulary. Preserve the approved Supabase Auth ADR and database model. Later resolved access/API decisions supersede historical proposal wording. There is no existing backend scaffold to extend.
- **Architecture:** Build a FastAPI factory/entry point, typed configuration, request IDs, redacted logging, shared error handling and synchronous SQLAlchemy infrastructure. Use synchronous routes with synchronous sessions. Feature modules own profiles, groups/memberships/invitations, expenses/shares, repayments and derived balances. Cross-module calls use public services sharing one request/use-case session. Repositories and services do not independently commit, roll back or close sessions; the transaction boundary completes before success is sent. Avoid unused modules and speculative abstractions.
- **Persistence:** Translate the approved application tables, constraints, indexes, same-group foreign keys, unique membership, append-only membership events and financial revisions into versioned migrations. Keep balances derived from non-deleted entries; no persisted balance table is approved. Separate migration-owner and non-owner runtime credentials; deny anonymous/client business-table access and runtime schema alteration/history mutation. Use local fixtures for managed identity references, never create or modify Supabase-managed auth internals in the hosted project.
- **Known reconciliation:** The historical dictionary describes retry persistence for creates only. The agreed API contract requires expense and repayment create, replacement and deletion. Extend supported operation values and canonical fingerprints to cover all six operations, target and expected version, and store each original success status/body atomically. Reconcile references to missing generated scripts, implementation rules and migration artifacts during foundation/persistence work; their documentation does not prove those artifacts exist. Do not repeat the schema interview.
- **Authentication:** Supabase SDK owns registration, Google/email sign-in, verification, reset, refresh and current-session sign-out. FastAPI validates signature, issuer, audience and expiry with a maintained verifier; issues no second token; derives actor identity from verified subject; and obtains account email/capabilities/verification from trusted auth data. No per-request session-revocation lookup is required: otherwise-valid copied tokens can remain usable until expiry. Current membership is checked on every group request and rechecked after acquiring mutation locks. Do not merge application users by email or implement manual identity linking.
- **Profiles:** Provision idempotently before operations needing profile references. Seed a display name once with a safe fallback, never overwrite an edited name on bootstrap/sign-in. Unverified authenticated users may bootstrap/read/edit their own profile but cannot perform group actions. Group-facing member data excludes email.
- **Groups and membership:** Create group, creator membership and join event atomically. Support INR, USD, CAD, GBP and EUR, with immutable IANA timezone. Active members have equal permissions; permit rename and pre-entry currency edits. Lock currency permanently at first financial entry. Departure/removal requires every direct balance involving the member to be zero; preserve membership and history. Valid rejoining reactivates the same membership. Final departure inactivates the group and revokes invitations; restoration is deferred.
- **Invitations:** Use cryptographically random bearer secrets, store SHA-256 digests only, return full URL only on creation, and expire links after seven days. Multiple reusable links may coexist. Verified preview reveals only the agreed confirmation data; explicit acceptance revalidates under group lock and is idempotent for active membership. Any active member may revoke links; issuer departure revokes their links. Tokens travel in POST bodies after URL extraction and are redacted from logs. Invalid/expired/revoked/inactive-group links share the unavailable response.
- **Transport and validation:** Implement the entire agreed versioned HTTPS JSON contract: account bootstrap/read/edit; group create/list/detail/update; member list/leave/remove; invitation create/list/revoke/preview/accept; expense and repayment detail/create/replace/soft-delete; merged transactions; direct balances; and process health. Preserve methods, statuses, resource fields and error codes from the contract. Money, including aggregates, is an integer-minor-unit decimal string; financial-entry totals range from 1 to 99999999999, allocated shares may be zero, and aggregate totals may exceed the entry cap. Percentages are integer basis points totalling 10000. Use UUID strings, calendar dates and UTC RFC 3339 audit timestamps. Enforce agreed trimmed name/label limits, enums and field rules; reject unknown fields. Use one standard error shape with code, message, fields, details and request ID.
- **Expense allocation:** Exactly one payer and nonduplicated participants from active group memberships on creation; payer need not participate. Equal/exact/percentage methods return final shares summing exactly to total. Use integer/rational calculations and largest fractional remainders with stable membership-ID tie-breaking. Reject method-inappropriate fields and invalid totals. Validate dates against the group's current local date, allowing backdating but no future dates.
- **Direct balances and repayments:** Net expenses and recorded repayments within each pair and group, never reroute debts or mix currencies. Payer's own share produces no self-debt. New repayment requires two distinct active parties, existing debt in the sender-to-recipient direction and amount no greater than current corrected debt. Backdating controls display order, not historical replay. Cash requires a null label; other requires a trimmed 1–100 character label. Repayments record external payments, never spending or money transferred by SpendWise.
- **Corrections:** Any active member may correct or soft-delete financial entries. Start versions at 1, increment for correction/deletion, require expected versions and return a conflict with current version when stale. Record full immutable before/after snapshots, shares, actor and time in the same transaction. Corrections may reverse debt between active members. Repayment parties are fixed; amount/date/metadata corrections and deletion do not reapply the new-payment cap. Correct wrong parties by deletion and normal new creation. Existing expenses may retain already-referenced departed members but cannot newly select them; all financial corrections/deletions must leave every departed member's direct balances zero. Hide deleted details with 404, omit them from ordinary lists/balances and retain history; no restoration endpoint.
- **Retries and concurrency:** Require UUID Idempotency-Key for all expense/repayment writes. Scope uniqueness to actor/key and fingerprint operation, target and canonical validated payload, including expected version. Exact replay returns original status/body even after subsequent edits/deletion, after current-access checks but before stale/deleted-entry checks. Changed command under the same key conflicts; another key is an ordinary new attempt. Retain successes for the MVP lifetime; roll back failed reservations. Serialize relevant membership/financial changes through group locks and recheck authorization. Commit entry, shares, versions, history, currency lock and retry result atomically. Concurrent duplicates yield one committed result; conflicts, races and commit failures must preserve invariants. Other writes have ordinary semantics, except explicitly idempotent profile bootstrap and invitation acceptance.
- **Reads:** Return separate owed/receivable summaries and positive pairwise debts. An expense row's position is caller payment minus caller allocated share for that expense, independent of repayments; include payer/display metadata and a fixed keyword icon mapping with generic fallback. Repayment rows include parties/payment metadata. One response's summary/balances share a consistent read snapshot; separate requests may observe later commits. Lists use items/next_cursor, default limit 30 and maximum 100, rejecting invalid or wrong-resource/filter cursors. Transactions sort descending date, creation timestamp, type and UUID; groups descending creation timestamp/UUID; members ascending first-joined timestamp/UUID; invitations descending creation timestamp/UUID. Paging reflects current data, so refresh restarts from page one after writes/backdating/edits/deletes. No live updates or exact count required.
- **Build sequence:** Follow foundation → persistence/access boundary → authentication/profiles → groups/joining → financial core → completed reads → deployed handoff. Add the agreed tests alongside each milestone using shared fixtures/scenario groups. Financial endpoints include retry/version/history protections from their first implementation. Maintain a compact route-to-scenario checklist. This specification is the parent scope for later implementation-sized tickets; it does not create a second milestone sequence.
- **Test environment:** Select a currently free-compatible FastAPI host during implementation and create a separate Supabase project for disposable accounts/data. Accept sleeping services and slower startup. Verify current pricing/payment requirements, HTTPS, Python/container support, outbound connectivity and connection/pooling limits rather than assuming provider availability. Ask before any paid choice or enabling charges. Configure auth providers and explicit test callbacks; a minimal SDK harness can exercise auth before screens exist. Keep runtime secrets server-side, provide a secret-free configuration template, apply migrations explicitly with migration credentials and document revision/health/logs/startup limitations. Recovery is compatible-code redeployment or rebuilding designated test resources from migrations/seed data, not an implied database downgrade or production backup guarantee.

## Testing Decisions

The user already approved this seam and minimal-test plan. Preserve it without another test-design interview. This specification writes no test code and reports no passing tests.

- **Primary seam:** Real application API requests exercising validation, token verification, transaction services and SQL against one disposable real PostgreSQL database migrated from empty. Use the intended non-owner runtime role. An isolated privileged fixture connection may seed identities, inspect history, inject failures and clean up. Use actual PostgreSQL connections for concurrency; no mocked repositories, production-money helpers as expected-value generators, or SQLite emulation.
- **Good tests:** Assert observable responses and persisted outcomes using known literal expectations or independently derived tables. Share builders, isolate scenario data, freeze the application clock for boundary dates and synchronize race cases explicitly. Cover a distinct risk once at the highest useful seam; avoid duplicate unit/service/repository/API assertions or a numerical coverage target. Focused direct SQL/grants checks supplement the API seam where permissions/integrity cannot be proved through HTTP alone.
- **Prior art:** There is no executable test suite in the current checkout. The approved verification document supplies the scenario design, fixtures, literal money examples and readiness gates. Reuse one runner and one documented command selected during implementation.
- **Scenario 1 — identity/group lifecycle:** Profile bootstrap/name preservation, account fields, unverified profile versus group access, group edits/currency/timezone, invitation lifecycle and repeated acceptance, private roster, departure/removal/rejoin, issuer revocation and final inactivation.
- **Scenario 2 — financial journey:** Three split methods, deterministic/zero shares and payer outside participants; expense positions; direct debts and currency isolation; partial/full repayments and metadata; correction after repayment, fixed repayment parties and creation-cap distinction; both entry types' revisions/soft deletion; permanent currency lock; zero-net-but-unsettled departure and departed-member protection.
- **Scenario 3 — validation/access matrix:** Compact request mutations for token signature/issuer/audience/expiry, verification, outsider/removed/wrong-group access across every protected route family including replay; money/splits/names/labels/enums/IDs, currencies/timezones/local-date boundaries, required retry/version values, overpayment/direction. Check standard errors and unchanged financial state/history after rejected writes.
- **Scenario 4 — reads/pagination:** Mixed entries tied on date/time with deterministic IDs, no missing/duplicate results in unchanged data, deleted omission and positions/summaries; shared paging assertions for all list families, empty results, limits and wrong cursors; refreshed current data after changes and consistent values within one response.
- **Scenario 5 — retries/conflicts/atomicity:** Parameterize creates/replacements/deletes across both entry types. Race identical keys for one original result; changed command conflicts, new-key semantics, replay after changes and denied replay after removal; same-version edit race, competing repayments and write-versus-departure races. Inject mid-write/history/result and deferred commit failures; assert complete rollback, no success/retained key, and successful retry after removing the fault. Flaky races fail the gate.
- **Scenario 6 — persistence boundary:** Clean migrations and representative direct-SQL violations for same-group references, uniqueness, totals/shares and protected history; client-role business-table denial and runtime-role schema-change denial. Inspect persisted rollback/debt outcomes as well as HTTP responses.
- **Fixtures and anchors:** Seed verified A/B/C, unverified U and outsider X with repeatable UUIDs; use locally signed credentials with controlled signing keys through the real verifier. Use INR and USD groups and a compact table for all five currencies. Equal 100 over ascending A/B/C allocates 34/33/33; equal 1 allocates 1/0/0. Percentage 101 at 3333/3333/3334 allocates 34/33/34. A pays 1000 split A/B: B owes A 500; B repays 300: debt is 200; correct total to 400: A owes B 100. The expense row still describes only its corrected allocation. Equal opposing direct debts involving one member block departure despite zero net.
- **One deployed smoke walkthrough:** After automated success, use disposable accounts to verify HTTPS/health and examples; real email registration/verification/reset and Google sign-in through an SDK harness; two-user joining, expense, repayment, correction and refreshed persisted balances; current-session sign-out and accepted expiry limitation; denied removed-member access with an unexpired token; redacted logs and actual runtime configuration. Repeat for deployment/auth-configuration changes, without manually duplicating all financial boundaries.
- **Completion gate:** Every agreed API route succeeds at least once and protected routes receive shared access checks. All six groups pass on real PostgreSQL with no skipped financial/access/race/rollback cases; clean migrations/grants and deployed real-auth smoke pass. Supply actual evidence, matching request/response examples and OpenAPI, one-command suite instructions, test-data setup/reset, reachable HTTPS API, public client configuration/auth callback requirements and recovery notes. Six groups are a starting structure, not six individual tests or an excuse to omit behavior. Add regression cases only for distinct uncovered risks or bugs.

## Out of Scope

- Application, test, migration or deployment execution during this specification task.
- Detailed screens, frontend implementation, mobile token-storage design, Android/iOS distribution and public app-store release. Later frontend work uses React Native, Expo and TypeScript.
- Personal expense tracking/aggregation, working Charts, Activity/history browsing, budgets, notifications, workers and live updates. Deferred UI placeholders do not require backend endpoints now.
- Multiple payers, mixed-currency expenses, currency conversion, debt simplification, money transfers and recipient confirmation.
- Account deletion, login-email changes, permanent group deletion/restoration, financial-entry restoration, manual account-linking UI and sign-out everywhere.
- A second auth/session system, application-managed Supabase auth internals, production backup/PITR promises or unapproved paid services.
- Reopening approved design interviews or multiplying tests across layers without a distinct failure mode.
